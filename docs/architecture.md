# Architecture

**Status:** target design, not implemented product behavior, except where marked implemented. Implemented product IPC is read-only (system, System page, Storage page, Developer page, storage discovery, the Cleanup scan) except asking an app to quit (ADR-009) and Cleanup's approved moves into quarantine, restores and permanent deletes (ADR-012). Persistence: the appearance preference in WebView storage, and the local history in SQLite (ADR-006).

## Boundaries and dependency direction

Tauri 2 hosts a React/TypeScript UI and a Rust backend. UI components depend on frontend feature/application code and typed contracts. Frontend IPC adapters call only narrow Tauri commands. Rust commands validate and map IPC DTOs, then call domain modules. Domain policy owns safety decisions; repositories own persistence; adapters isolate OS and external integrations. Dependencies point inward. No frontend unrestricted filesystem or shell API.

## Modules

- Frontend: `app` composition, shared components, feature views, hooks, `lib` IPC adapters, `contracts` request/response types.
- Rust: `commands` transport boundary; `system_monitor`; `scanner`; `classifiers`; `safety`; `cleanup`; `quarantine`; `persistence`; `audit`; `background`; `errors`; `integrations/docker`.
- SQLite: local operation history, activity log, preferences and excluded folders with explicit versioned migrations (`persistence`; see below and ADR-013). The appearance preference lives in WebView storage.

The repository keeps one desktop app; packages are added only when a real reusable boundary exists.

## Typed IPC and errors

IPC request/response DTOs must be typed on both sides and validated at the Rust boundary. Do not trust frontend types as runtime validation. Commands return stable, non-sensitive error categories; internal diagnostics avoid leaking stack traces, secrets or sensitive paths. Cancellation and partial results must be explicit in contracts.

## Implemented: system metrics (read-only)

`get_system_metrics` (Rust `commands`) returns one snapshot from `system_monitor`, including the process summary. It is declared in `build.rs`'s app manifest but, since no screen uses it, its permission is not granted in `capabilities/default.json`; a call from the WebView is refused. The same applies to the chosen-folder scan commands below.

- **Collection:** `system_monitor::collector::SystemSampler` uses the `sysinfo` crate (no shell execution, no privileges, no file contents). It lives in Tauri managed state behind a `Mutex` because CPU usage is a delta between two refreshes; a refresh sooner than `sysinfo::MINIMUM_CPU_UPDATE_INTERVAL` keeps the previous reading.
- **Availability:** `system_monitor::to_metrics` maps raw values into `Reading::Available` or `Reading::Unavailable { reason }`. `sysinfo` reports `0` when an OS call fails, so a zero memory or disk total is *unavailable*, never a zero reading. A genuine 0% CPU stays available.
- **Values:** CPU is the all-core average over the sample window. Memory `used` is app + wired + compressed memory and `available` is the XNU "available" figure (active + inactive + free), so the two can sum to more than the total. The disk is the volume mounted at `/`; `available` is macOS's "available for important usage" (includes purgeable space, as Finder shows) and `used = total − available`.
- **Battery:** `system_monitor::battery` reads the internal battery from IOKit power sources (`IOPSCopyPowerSourcesInfo`, via `objc2-io-kit`, macOS-only; other targets report unreadable). No battery is `unavailable: notPresent` and the Overview hides the card; an unreadable, incomplete or out-of-range reading is `notReported`. Charge is current ÷ max capacity. State is charging, charged, not charging (on power but held) or discharging. The estimate is time to full while charging and time to empty while discharging; macOS's `-1` ("calculating"), `0` and implausible values (> 48 h) become `null`, never 0 minutes. Battery health and cycle count are not read.
- **Processes:** `system_monitor::processes` reads each process's name, PID, cumulative CPU time, memory and executable path through `sysinfo` (no command line or user). The long-lived sampler never requests executable paths. For each newly seen process identity (PID + start time), a short-lived `System` reads the path, `app_name_from_exe` derives the outermost bundle name (a `Name.app` component immediately followed by `Contents`, so plain directories ending in `.app` do not count; bundle layouts without `Contents`, such as iPhone and iPad apps on Apple silicon, are not recognized and group by process name instead), and the lookup is dropped. Only the derived names are kept, keyed by identity and pruned when processes exit; paths are never retained, placed in a DTO, stored or logged. Per-process CPU is computed from the change in cumulative CPU time over the same window as total CPU, not from `sysinfo`'s `cpu_usage`, which keeps its previous value for a process that did no work and would leave idle processes ranked high. It is a share of one core (as in Activity Monitor), so it can exceed 100%, capped at 100% × logical CPUs. A PID whose start time changed (reuse) or whose counter went backwards has no CPU reading. Processes reported with zero memory have no readable value; they are counted as `unreadableCount` and never ranked or shown as 0. These are usually processes macOS withholds from unprivileged apps (for example `WindowServer`, `launchd`; on the development Mac all such processes also had an unreadable owner), but the cause is not checked per process, so the UI states it as the usual reason rather than as fact. Processes are also grouped into apps: by bundle name for processes inside a `.app`, otherwise by process name, with the two kinds kept as separate keys so a CLI never merges into an app of the same name. An app's CPU is the sum over members that have a reading (`null` if none yet), capped at 100% × logical CPUs, with `cpuMeasuredCount`; when fewer members are measured than the app has, the UI shows the value as a lower bound ("≥", read as "at least") and explains why; its memory is the sum of members' resident memory, which can count shared memory more than once, and the UI says so. The top 5 processes and top 5 apps, each by CPU and by memory, are sent so the Overview's Apps/Processes and CPU/Memory toggles switch instantly; CPU ranking is empty until a second sample exists. Names are trimmed to 100 characters and rendered as text. No process action exists.
- **Contract:** `src/contracts/systemMetrics.ts` mirrors the DTO and `parseSystemMetrics` validates it at runtime; `src/lib/systemMetricsIpc.ts` maps failures to `backendUnavailable`, `metricsUnavailable` (stable backend code), `invalidResponse` or `unknown`.
- **Refresh:** the Overview polls every 5 s while the document is visible, single-flight (the next request is scheduled only after the previous one settles, and a poller restarted by a visibility change or remount joins a still-pending request), plus manual refresh. Hidden windows and unmount stop the timer, so polling also stops while Settings is shown. A failed refresh keeps the last readings marked stale.

## Implemented: Developer page data (read-only)

Three commands, each with its own capability permission. Docker decision record: [ADR-011](adr/ADR-011-docker-disk-use.md).

- **`start_developer_scan(channel)`** (`developer`): caches, then projects, then Docker.
  - **Caches:** a fixed catalog (`developer::catalog`) of known developer caches and toolchain folders:
    - Xcode DerivedData, Archives and DeviceSupport, plus simulator devices and runtimes
    - Homebrew
    - npm, pnpm, Yarn and Bun
    - Gradle and Maven
    - CocoaPods
    - pip
    - Cargo and rustup
    - Go modules and the Go build cache

    The home folder (like every search root, Docker's disk-image folder and the version-file folders) is opened from `/` one component at a time with no symlink anywhere on the path (`measure::open_absolute`), so the lexical path checked against the mount table is the one opened; the table is re-read before each component and after any step onto another volume (the remaining check-to-open race is in the threat model). Each cache location is opened from that handle on the home folder (or `/`), one component at a time relative to each open parent, with no-follow opens, identity checks and the base's volume only (`measure::open_beneath`). The mount table is read again before each location. `developer::measure` then sizes it from that handle: it follows no symlinks, stays on the same volume, records file counts and keeps the three largest parts plus one running total for the rest, and holds one hard-link set for the whole scan. pnpm links store packages into each project's `node_modules`, so the store and the projects aren't counted twice. Caches under 1 MB, or under a non-local mount, aren't listed.
  - **Versions:** read from files only (Xcode's `Info.plist`, npm's `package.json`), without following symlinks, and kept only if they look like a version. Other tools show their location instead.
  - **Projects:** `developer::projects` searches the home folder (without Library or the Trash) and any folders added through the macOS folder picker (`add_developer_folder`). It looks for marker files:
    - `package.json` (Node.js, or Next.js with `next.config.*`)
    - `Cargo.toml`
    - `pom.xml`
    - Gradle build files
    - Python project files
    - `Podfile`
    - `pubspec.yaml`
    - `composer.json`

    For each project it records the build folders those tools make. The search reads only folder listings, never descends into build folders, `.git` or hidden folders, stays within 8 levels and 500 projects, and stays on the volume. It is depth-first with one open folder per level (at most 9 open at once) and checks for cancellation on every entry. The mount table is read again before each root; a root under a non-local mount, or any root when the table can't be read or the folder can't be opened, is skipped and reported (`skippedRoots`). Build folders are measured while the search holds the project's open folder, opened relative to it on the same volume, never reopened by path. For each repository it reads the last entry of `.git/logs/HEAD` (at most the final 8 KB), opened through `.git` and `logs` on the project's volume, for the time of the last commit.
  - **Docker:** `developer::docker` sends one read-only `GET /system/df` over the engine's local socket, with size limits and one 10 s deadline across both sockets. The connect is non-blocking and reads time out every 100 ms, so the exchange (on the scan's thread, with no helper thread) ends at the deadline or when cancelled; a cancelled scan doesn't ask at all (`notChecked`). A reply missing a section, or with sizes Docker didn't compute, is marked incomplete and shown as a minimum. When the engine doesn't answer, only the size of Docker Desktop's disk image is reported. Kleari never runs a Docker command.
- **`cancel_developer_scan`** stops the scan. The page keeps the last complete one.
- **`add_developer_folder`** opens `NSOpenPanel` from Rust. The folder stays in `DeveloperState` for the session; the frontend gets only its name, and a scan follows.

`src/contracts/developer.ts` validates every response (bounds, parts not larger than their folder, project totals). `src/features/developer/developerView.ts` maps it to the screen:
- catalog names and explanations, and risk labels: low, check first, Xcode-managed, or active (a file in it, or the folder, open in some app; never suggested, and checked again before anything moves);
- totals, with the share of used space taken from the Storage overview; when any part is a minimum, or the project search missed something (a skipped location, unreadable folders, the 500-project cap), the total shows "≥" and the share "at least", and the project total shows "≥" for the search cases;
- Docker's states: not installed, not running, running (complete or a minimum), and not checked.

Each cache with one location and each build folder carries a `reviewId`; the scan's `review_items` (path, `lstat` identity, measurement) stay in `DeveloperState`. The page's selection (low and check-first entries only; "Select low risk" adds low only) calls `send_developer_items_to_review(ids)`, and Cleanup classifies them again in Rust. A project sends each of its build folders.

## Implemented: Processes page data

Two commands in the default capability. Release builds include them by the product owner's decision. Each delivered or refused request is recorded in the activity log with the app's name; see [ADR-009](adr/ADR-009-process-quit.md) and [ADR-013](adr/ADR-013-settings-activity-dashboard.md).

- **`list_processes`** (`system_monitor::process_sampler`, pure grouping in `process_list`):
  - **Read once every 2 s while the page is shown.** Every process (`sysinfo`: name, owner UID, executable, cumulative CPU time, resident memory) and this account's regular apps (`NSWorkspace.runningApplications`, on the main thread).
  - **Rows:**
    - A regular app is one row with every process inside its bundle folded in; its PID is the app's own process.
    - A process inside some other bundle joins that bundle's row; every other process is its own row.
  - **Kinds:**
    - *App*: a regular app.
    - *Background*: this account's own process outside macOS's folders.
    - *System*: another account's process, or one running from `/System`, `/usr/libexec`, `/usr/sbin`, `/sbin` or `/Library/Apple`.
  - **CPU:** the change in cumulative CPU time over the polling window, summed over the members that have a reading. Fewer readings than members make it a minimum. CPU is withheld on the first sample and after any gap over 6 s, so a long average is never shown as current.
  - **Other accounts' processes:** macOS reports their memory and CPU time as 0 to Kleari. Apple's setuid `/bin/ps` fills in memory, CPU time and owner (`system_monitor::ps`, [ADR-010](adr/ADR-010-system-ps.md)): fixed arguments, no shell, an empty environment, a 1.5 s limit and bounded output, parsed as untrusted text.
  - **Unreadable processes:** anything still without a memory value is counted, not listed. The cause isn't checked per process.
  - **Row limit:** the 50 busiest plus the 50 largest are sent.
  - **Detail fields:**
    - Owner: `getpwuid_r`.
    - Start time.
    - Thread count: `proc_pidinfo(PROC_PIDTASKINFO)`; macOS refuses it for other accounts, which shows as "Not available".
    - Location: the bundle or executable, with `~` for the home folder.
  - **`canQuit`** (`may_quit`): true only for another regular app of this account, outside macOS's folders (so not Finder or Terminal), whose process identity (`proc_pidinfo` BSD info: start time in microseconds and owner) could be read and is still the sampled process. Bundles are resolved through symlinks first, walking `storage::fsdir` directory handles (no-follow opens relative to the open parent, `fstatat`, `readlinkat`), never at or below a mount that the mount table, read just before (`getmntinfo(MNT_NOWAIT)`), reports as non-local; apps there aren't quittable. A volume mounted after that read could still be looked up once (ADR-009). The row then carries that start time as `quitToken`, and the sampler keeps token → (PID, resolved bundle) for the latest list only. `ps` runs on macOS only.
- **`quit_app(pid, quitToken)`** (`system_monitor::running_apps`): Kleari's only action that changes anything. It accepts only a token the latest list issued for that PID; then every check and the request run in one main-thread step:
  - It refuses Kleari's own PID.
  - It requires the PID's identity to equal the token and belong to this account.
  - It looks the app up again (`NSRunningApplication`) and requires a regular app that hasn't terminated, whose resolved bundle equals the recorded one and lies outside macOS's folders.
  - It reads the identity again, then sends the polite `terminate` request.
  - Outcomes: `requested`, `notRunning`, `notAllowed` or `declined`. No force quit and no signals.

`src/contracts/processes.ts` validates every response (row limit, CPU consistency, and that `canQuit` appears only on another app). `src/features/processes/processesView.ts` maps it to the screen (live, waiting, paused, stale or unavailable; CPU history only from samples taken, with gaps). `useProcessMonitor` (app level, from launch) polls single-flight every 2 s while Processes is on screen and every 5 s otherwise, while Kleari is open to look at (window visible or menu-bar popover open, `useKleariInView`) and not paused; `useProcessesPage` marks the page as on screen. The page takes the quit target only from the latest successful list.

## Implemented: System page data (read-only)

The v2 System page uses four commands, each with its own capability permission:

- **`get_system_activity`** (`system_monitor::activity`): CPU, memory, swap, memory pressure (`kern.memorystatus_vm_pressure_level`), thermal state (`NSProcessInfo.thermalState`; no temperature, which has no public API on Apple silicon), battery (the same IOKit power-source reading as `get_system_metrics`), and network and startup-disk byte rates. Its `ActivitySampler` is separate from `SystemSampler` and never enumerates processes, so it is cheap enough to poll once a second. A sampling window longer than 3 s (first visit, pause, hidden window) is reported as warming up and only resets the baseline, so a long-period average is never shown as current; the page stays "Waiting" until a short-window reading arrives. Rates come from deltas of cumulative counters; a counter that goes backwards or no elapsed time is "no reading", never a spike. Network totals skip loopback and tunnel interfaces (a VPN's bytes also cross the physical interface). Disk rates use the root volume only: every APFS volume on a disk reports the same disk-wide counters.
- **`get_system_details`** (`system_monitor::details`): model identifier (`hw.model`) with a bundled marketing-name table (`names.rs`; unknown identifiers show the identifier), chip (`machdep.cpu.brand_string`), core counts including performance/efficiency clusters (shown only when they add up), GPU cores (IORegistry `AGXAccelerator gpu-core-count`), memory size, macOS version (`kern.osproductversion`) with a name table for released versions, startup volume, boot time, battery cycle count and capacity (IORegistry `AppleSmartBattery`, `NominalChargeCapacity / DesignCapacity`, capped at 100), and the display (CoreGraphics physical size and built-in flag, AppKit's localized name, read on the main thread).
- **`list_startup_items`** (`system_monitor::startup`): launch agents and daemons from the three standard folders. Each plist is opened with `O_NOFOLLOW`, read only if the handle is a regular file, at most 256 KB each and 500 per folder; unreadable or malformed ones are counted, and a folder that exists but can't be listed is counted separately (a missing folder is just empty). Each item's program is `present`, `missing` or `notChecked`: the check never follows a symlink and never touches a volume the mount table doesn't report as local, so it can't cause network I/O. The plist's `Disabled` key is reported as such; System Settings overrides aren't visible. macOS's Login Items list (Background Task Management) needs administrator access and is not read.
- **`open_system_settings`** (`system_settings.rs`): opens Software Update, Login Items or (for the Storage page) Privacy & Security › Full Disk Access. The pane is a fixed enum; the frontend never supplies a URL.

`src/contracts/systemPage.ts` validates every response. `src/features/system/systemView.ts` is the pure mapping into what the screen shows (live, paused, waiting, stale or unavailable), and the app-level `useSystemMonitor` polls activity every second while System is on screen and every 5 s otherwise, while Kleari is open to look at (window visible or menu-bar popover open) and not paused; details and startup items load once per visit. Chart history is only the samples taken; a gap longer than three intervals (pause, both out of sight) starts a new chart, so no history is ever filled in. No SMART status (it would need `diskutil`) and no update check (it would need the network).

## Implemented: Storage page data (read-only)

The v2 Storage page uses three commands, each with its own capability permission. Design and safety rationale: [storage-discovery.md, Storage page analysis](storage-discovery.md#storage-page-analysis).

- **`get_storage_overview`** (`storage::volume`): the startup volume's name and capacity from Foundation's volume resource values. Available is `NSURLVolumeAvailableCapacityForImportantUsageKey` (free plus purgeable, as Finder shows) and used is total − available. Purgeable space is that figure minus `NSURLVolumeAvailableCapacityKey` and is labelled an estimate; if the purgeable-aware figure is missing, Available falls back to free space and purgeable is "not reported", never 0. Swap and the sleep image are the on-disk sizes of the files directly in `/System/Volumes/VM` and `/private/var/vm`, listed without following symlinks (`statfs` can't be used: on APFS it reports the whole container for every volume). Full Disk Access is `granted` if any of `~/Library/{Mail,Safari,Messages}` opens, `notGranted` if one is refused and none opens, otherwise `unknown`; the folders are opened and closed, never listed, and macOS doesn't prompt for them. Local Time Machine snapshots aren't shown: their sizes need administrator access, and macOS counts them in purgeable space.
- **`start_storage_analysis(channel)`** (`storage::analysis`): walks fixed locations read-only in four steps: Applications; the home folder; `/System` and `/usr`; `/Library`, `/opt`, `/private/var` and `/usr/local`. The frontend sends no path. The walk reuses `fsdir`'s no-follow handle traversal, never enters another device and counts hard links once; past the tracking limit a hard link isn't counted at all. Anything not counted marks its folders and its category `lowerBound`, so a total is never inflated by a duplicate. Exclusions keep each byte counted once: `/System/Volumes` (the Data volume reports the same device as `/`), `/usr/local` under `/usr`, and `/private/var/vm` (shown as swap and sleep image). Cloud folders (`~/Library/CloudStorage`, `~/Library/Mobile Documents`) are skipped so listing them can't make a provider download. The result is a folder tree (4 levels below each location, 12 largest subfolders of at least 100 MB per folder, the rest combined into "other items"), totals for six location-based categories with each one's 3 largest items, the 50 largest files of 1 GB or more (name, folder shown as `~/…` or absolute, size, modified time, category and a lock for Docker data, simulator runtimes and macOS files), and coverage counts. Anything unreadable marks its folders as minimums. Progress (step, bytes counted, finished steps' totals) streams at most every 250 ms; one analysis runs at a time (`analysisInProgress`).
- **`cancel_storage_analysis`**: stops the walk; the partial result comes back marked `cancelled`, and the page keeps the last complete one instead.

`src/contracts/storageAnalysis.ts` validates every response (tree size and depth, children not larger than their folder, step totals equal to their folder). `src/features/storage/storageAnalysisView.ts` is the pure mapping into the screen: used space the analysis didn't count is shown as "Not measured" rather than spread over the categories, and progress is bytes counted ÷ used space, capped at 99% while running. If used space is unknown, the dialog shows only the step ("Step 2 of 4"), never a percentage. Category totals and shares that are minimums are labelled "at least". `useStorageAnalysis` holds the running analysis and last result at the app level (so they survive navigation) and cancels on unmount; `useStorageOverview` reads capacity on each visit, when the window returns to the front and after each analysis. Nothing is stored.

## Implemented: navigation and appearance

- **Window material:** the main window is transparent and uses Tauri window effects: Liquid Glass Regular on macOS 26+, falling back to sidebar vibrancy on macOS 14–15. It has an overlay title bar with a hidden title, and a control-free `data-tauri-drag-region` strip (`.v2-titlebar`, `core:window:allow-start-dragging`) for moving the window. Each screen's content scrolls inside a `ScrollBody`, a keyboard-focusable region named after the screen (`tabindex="0"`), below the page header, so no scrolled control passes under the strip. `main.tsx` sets `data-native-window` on the root when running in Tauri, and CSS then lets the material show through the sidebar only. See [ADR-008](adr/ADR-008-native-window-material.md).

- **Release and development interfaces:** release builds load `src/v2/ReleaseApp.tsx`: the v2 shell with only the screens backed by real data (Cleanup with Review and Preview, Quarantine, Storage, System, Developer, Processes, and Settings with the appearance choice only, `AppearanceSettingsScreen`). Development builds load `V2App`, which uses the same live screens and adds every other v2 screen with sample data. The live routes live in `src/v2/liveRoutes.tsx`, which imports no sample data. `pnpm check:release-bundle` (CI) fails if `main.tsx` stops gating `V2App` behind `import.meta.env.DEV`, if any import reachable from `main.tsx` (static or dynamic, skipping only that one development import) reaches a file in `src/v2/sample/` (`scripts/release-graph.mjs`), or if the sample-data marker appears in the built bundle. The window's minimum width (900 px in `tauri.conf.json`) matches the layout's minimum, checked by a test.
- **Navigation:** `src/v2/shell/routes.ts` maps hashes to destinations with no router dependency; release builds allow only `#cleanup`, `#review`, `#preview`, `#quarantine`, `#storage`, `#system`, `#developer`, `#processes` and `#settings`, and anything else opens Storage. The sidebar uses links with `aria-current="page"`; ⌘, opens Settings (`src/app/navigation.ts`). After a route change (not on first load), focus moves to the destination's page heading (`tabindex="-1"`) so keyboard and screen-reader users land on the new page. Navigation never starts an action.
- **Appearance:** `src/features/settings/appearance.ts` holds the System / Light / Dark preference. It is saved in WebView `localStorage` under `kleari.appearance`, an interim per-Mac store until the SQLite settings store (ADR-006) exists. `loadAppearance` reports how the preference was obtained (`saved`, `default`, `unreadable`, `invalid`); unknown values or a storage error fall back to System and Settings says so. Settings shows "Saved on this Mac." only after a real read or write; a failed save is reported and the choice applies only until the app restarts. The preference is applied before first paint (`main.tsx`) by setting or removing `data-theme` on the root element, and the native title bar follows via `getCurrentWindow().setTheme()` (`null` = follow macOS), which needs the `core:window:allow-set-theme` capability permission. A failed title-bar update is reported without undoing the page change.

## Implemented: storage discovery (read-only)

Design and safety rationale: [storage-discovery.md](storage-discovery.md). No screen uses these commands since the release interface moved to v2, so their permissions are not granted. Cleanup adds folders with its own command (`add_cleanup_folder`), using the same picker.

- **Grants:** `choose_scan_folder` opens macOS `NSOpenPanel` from Rust on the main thread (`storage::picker`, via `objc2-app-kit`). The canonicalized folder and its device and inode are kept in `StorageState` under a sequential grant ID; the frontend receives only `{ grantId, displayName }` and never sends a path. Grants are in memory for the session only.
- **Scan:** `start_scan(grantId, channel)` opens the root with no-follow semantics, checks its identity on the opened handle (fails closed with `rootChanged`), and walks it read-only on a blocking thread (`storage::scanner`):
  - folders are opened by handle relative to their open parent (`storage::fsdir`: `fstatat(AT_SYMLINK_NOFOLLOW)`, then `openat(O_NOFOLLOW | O_DIRECTORY)`, then an identity check on the opened handle), so a folder swapped for a symlink mid-scan is never followed. `fsdir` is the feature's only `unsafe` code
  - the walk is depth-first and holds only the current path's folders open; memory is bounded by `ScanLimits` (128 open levels, 100 top-level rows plus a combined row, an index of up to 250,000 files holding at most 64 MiB of path text, 1,000,000 hard-link identities)
  - symlinks are never followed; folders on other devices are not entered; hard links are counted once
  - sizes are allocated bytes (`st_blocks × 512`, matching `du` and Finder)
  - unreadable entries are counted, never treated as zero
  - progress streams over a Tauri channel at most every 250 ms; `cancel_scan` sets a token checked per entry, returning partial results marked cancelled
  - only one scan runs at a time (`scanInProgress`)
- **Results and filters:** the summary holds totals, coverage counts, a top-level breakdown and the 50 largest files. The backend keeps an index of up to 250,000 files (at most 64 MiB of path text) from the last scan in memory. A file is admitted only by evicting strictly smaller ones, decided before any eviction, so larger files are favoured but a long-path file can be left out. The UI presents figures as exact, as lower bounds ("At least", "≥" for cancelled or partially unreadable scans) or as approximate ("About", "≈" when hard links may be double-counted), and shows shares only when the total is exact. `query_scan(grantId, filter)` re-ranks within name, type (by extension), top-level row `id` and minimum-size filters without rescanning, on a worker thread. Filters are validated in Rust (`deny_unknown_fields`, a fixed type set, an existing row id, a name of at most 200 characters). Non-UTF-8 names are displayed with `\x{XX}` escapes. The index is dropped when the next scan starts.
- **Commands** are declared in `build.rs`; each has its own capability permission. The frontend contract is `src/contracts/storage.ts` (runtime-validated, including every progress message); `src/lib/storageIpc.ts` maps the stable error codes. The scan state machine (`features/storage/storageState.ts`) lives at the app level, so a scan and its results survive navigation.

## Implemented: Cleanup, Review, Preview and Quarantine

Decision record: [ADR-012](adr/ADR-012-cleanup-and-quarantine.md). Sixteen commands in `cleanup_commands`, all in the default capability. The frontend sends only scan options, fixed enum values and opaque hex IDs (`check_ids`: at most 10,000, 1–64 hex digits).

- **Scope** (`cleanup::scope`): `get_cleanup_scope` lists the folders each mode reads:
  - `~/Library/Caches` and `~/Library/Logs` (Standard and Deep);
  - `~/Library/Developer` and the home folder's projects (Developer);
  - Downloads, Desktop, Documents and Movies (Deep);
  - folders added with `add_cleanup_folder` (the macOS panel).

  Protected folders show their remembered access, or `fullDiskAccess` when Full Disk Access is on (`storage::volume::full_disk_access`), and are never read on a visit. `request_folder_access(folder)` opens and lists the folder once, which makes macOS ask, and remembers granted or denied in the history.
- **Scan** (`cleanup::scan`): `start_cleanup_scan(mode, options, channel)`.
  - Options are validated against the menu values (`deny_unknown_fields`).
  - Standard: app caches, logs and temp, package caches. Deep adds large and old files in granted and added folders. Developer: Xcode, simulators, `node_modules`, Docker (read-only `docker::read`).
  - Folders are opened with `open_absolute`, with the mount table checked and no symlink anywhere on the path. Children are opened relative to their open parent with identity checks and measured with `measure_dir`, which now also reports the newest modification time for log and temp age.
  - `node_modules` comes from `projects::discover` over the home folder and the added folders. The lockfile check is `fstatat` relative to the project's open folder. If that finds nothing, `intake::has_lockfile` looks upward for a workspace root whose patterns include the project (`pnpm-workspace.yaml` or `package.json` `workspaces`, read no-follow, at most 256 KB). Another project's lockfile ends the search, as do the folder holding `.git`, the home folder and 8 levels.
  - Progress (`{ step, items, bytes }`) streams at most every 150 ms while a step finds items, including during the project search.
  - Large and old files are a depth-first handle walk, 16 levels deep and at most 200 of each. It skips bundles, Library, `.git` and `node_modules`.
  - Running apps (bundle IDs, `running_bundles`) feed the policy.
  - EPERM and EACCES are counted and reported as `needsFullDiskAccess`. Unopenable roots are reported as skipped.
- **Policy** (`cleanup::policy`): `assess` decides risk, certainty, eligibility, the reason and the evidence (as codes the frontend words). `within_bounds` fixes the places each kind may come from. See ADR-012 for the table.
- **Review** (`CleanupState`): the last scan's candidates plus items sent from Developer and from Storage (`add_storage_file_to_review(reviewId)`: always inspect only). `get_cleanup_review` returns findings with `~/…` locations only. `reveal_review_item` shows an item in Finder if its identity is unchanged.
- **Preview and approve** (`cleanup::execute`): `create_cleanup_preview(ids)` and `approve_cleanup_preview(previewId, channel)`, as described in ADR-012. Approval takes the single operation lock (`QuarantineState`) and reads the running apps fresh. If that read fails, it fails closed (`cleanupUnavailable`). Outcomes: `noPreview`, `stale { changed }`, `historyUnavailable`, `finished { items }` with each item `moved` (in quarantine and fully recorded), `unconfirmed` (the rename happened but couldn't be checked or fully recorded; the record stays `moving`), or `failed { reason }` (nothing moved).
- **Quarantine** (`quarantine`): `Store` moves, restores and deletes through `quarantine::fsops`, the only file-changing syscalls in Kleari: `renameatx_np(RENAME_EXCL)` / `renameat2(RENAME_NOREPLACE)`, `mkdirat` 0700, and a handle-based `unlinkat` walk that never follows symlinks. `list_quarantine` reports each held item's status: restorable, conflict, folder missing, missing from the folder, pending (an unresolved `moving`/`restoring` record), or unverified (the folder can't be inspected, or something else is under its name). Pending and unverified items can't be restored or deleted. `restore_quarantine_items` returns per-item outcomes, including `unconfirmed`. Restore checks what arrived at the original place and moves a replacement back. The delete walk checks the recorded identity itself and empties a folder only through its verified handle. `delete_quarantine_items(ids, channel)` deletes one at a time and `stop_quarantine_delete` stops after the current item. `reveal_quarantine_item(id, withOriginal)` shows the item, and optionally whatever is at its original place. Restore, the original in Show in Finder, and launch reconciliation use a stored original only if it passes `policy::restorable` for its category (`quarantine::Scope`: home, temp, and folders chosen in the folder panel this session); otherwise the restore is `notAllowed` and the item is listed unverified, or, for a build folder from an added folder, `needsFolder` until that folder is chosen again. `choose_restore_folder` opens the folder panel and grants the folder for restores only (kept in `QuarantineState`, never scanned) while holding the operation lock (`operationInProgress` otherwise, nothing granted), then reruns reconciliation. `list_quarantine` also reruns it whenever no operation runs. Settling holds the lock as `begin_settle`: operations (`begin`) wait behind it rather than fail, and a settle is skipped while an operation runs. Reconciliation settles from the quarantine folder regardless, and from the original place only in scope.
- **History** (`persistence`, `history`): SQLite (`rusqlite`, bundled) at `<app data>/history.sqlite3`, 0600, in a 0700 folder.
  - Migrations are numbered, run in transactions, and tracked with `user_version`.
  - `quick_check` runs on open. Corrupt files, newer schemas and failed migrations are left untouched and reported.
  - WAL and `synchronous = FULL`.
  - Tables: `quarantine_batch`, `quarantine_item` (original path as bytes, the added folder for a build folder outside the home folder, identity, state), `history_event` (counts, sizes, outcome and a subject such as a scan mode or an app's name; no paths), `history_event_item` (which quarantine items an event concerned, with each one's outcome), `folder_access`, `setting` (validated preferences), `excluded_folder`.
- **Settings and Activity** (`preferences`, `settings_commands`, `activity`, `login_item`, `notifications`; ADR-013): preferences are validated against the Settings page's choices and applied in Rust (Cleanup scans never open excluded folders and the minimum size filters each step, preview and approval apply both again, the Developer search skips excluded folders, Storage's large files drop excluded and recently changed ones); Open at login is `SMAppService.mainAppService`; notifications use `UNUserNotificationCenter`, only from an app bundle; `list_activity` returns up to 500 events with item lines as name and `~/…` folder; events past the retention period are deleted at launch and when it changes.
- **System monitor:** sampled from launch by an app-level hook (every 5 s off the System page, 1 s on it, while the window is visible or the menu-bar popover is open, and not paused), so System and the Dashboard open with readings and a chart labelled by the time its readings cover.
  - At launch, items left `moving` or `restoring` are resolved only from what the folders prove (`Store::resolve_interrupted`); records that can't be told are kept.
- **Frontend:** `src/contracts/cleanup.ts` validates every response, including the rule that an item that can't be selected always carries a reason. `src/lib/cleanupIpc.ts` provides the IPC calls. The app-level hooks are `useCleanupScan`, `useCleanupReview` and `useQuarantine`, and `features/cleanup/cleanupView.ts` maps their data to the existing v2 screens. Storage's "Scan in Cleanup" opens Cleanup with the mode chosen and never starts it.
- **`getmntinfo` is serialized:** its buffer is process-wide, and parallel scans could read a half-written table and fail closed. A static lock now guards the read.

## Implemented: menu bar, updates and uninstall (ADR-014)

- **`menubar.rs`:** the menu-bar item (Tauri `tray-icon`), the hidden `popover` window and its placement, close-to-menu-bar for the main window, and `open_main(destination)` / `hide_popover`. `menubar::active` (the item exists) is the only record of whether it is on; `menubar::set` applies a change on the main thread and waits for it. `set_preferences` changes the item before saving and puts it back if the save fails, one save at a time.
- **Popover frontend:** `main.tsx` loads `v2/PopoverApp` when the window label is `popover`. `features/menubar/usePopover.ts` reads only while the window has focus (the popover hides on blur); `features/menubar/popoverView.ts` maps the readings with the Dashboard's own `metrics`. `capabilities/popover.json` scopes it.
- **`updates.rs`:** `check_for_update` and `install_update` over `tauri-plugin-updater` (Rust only, no JS plugin). The update found by the last check is kept in `UpdateState`, so Install applies what was shown. `features/settings/useUpdates.ts` checks at launch when the preference is on; `v2/screens/settings/Updates.tsx` has the launch offer and the About rows.
- **`uninstall.rs` and `uninstall_kleari`:** the fixed list of Kleari's own locations, the running bundle (`app_bundle`), and `move_to_trash` (`NSFileManager trashItemAtURL`). The checks and their order are in ADR-014. `quit_kleari` exits.

## Implemented: scheduled scans and the Mouse module (ADR-015, ADR-016)

- **`schedule.rs`:** checks the `scanSchedule` preference once a minute from launch; `since_due`, `next_due_ms` and `decide` are pure and tested. A due scan runs `cleanup_commands::run_scan` (shared with `start_cleanup_scan`) with `ScanOrigin::Schedule`, under the same scan lock, and emits `scheduled-scan-finished`; `features/cleanup/useScheduledScan.ts` refreshes the review and activity on it. `get_settings` includes the schedule's next and last times.
- **`notifications.rs`:** a `UNUserNotificationCenter` delegate (set at launch) opens the review when a scan's notification is clicked (`menubar::open_at`) and shows notifications while Kleari is in front.
- **`mouse/`:** `config.rs` (the validated `mouse.v1` record and the key table), `engine.rs` (pure decisions: `Input` → `Output`), `tap.rs` (macOS event tap thread, glide thread, posting tagged events), `probe.rs` (the button finder's in-app `NSEvent` monitor, reporting only while the page listens) and `mod.rs` (`MouseState`, `get_mouse`, `set_mouse`, `request_mouse_access`). The frontend is `contracts/mouse.ts`, `lib/mouseIpc.ts`, `features/mouse/{useMouse,mouseView}.ts` and `v2/screens/mouse/MouseScreen.tsx`.

## Planned data flows

### Integrations and background work

Docker adapter is read-only inventory/recommendation. Optional AI provider is advisory, requires user consent and cannot authorize. Foreground monitoring is initial default. Background monitoring and notifications are future designs requiring permission, lifecycle, shutdown and privacy decisions.

## Trust boundaries and data flow

Untrusted sources include IPC payloads, filesystem names/metadata, scan results that may become stale, AI output, Docker responses and persisted data. Rust validates at boundaries. User grants define accessible scope, not automatic cleanup eligibility. All future paths require canonical/boundary checks and symlink-safe traversal; identity and policy are revalidated immediately before mutation. No content is uploaded by default.
